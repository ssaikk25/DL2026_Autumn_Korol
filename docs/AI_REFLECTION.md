# Рефлексия по использованию AI

Документ описывает опыт использования AI-инструментов в ходе выполнения задания и соответствует
части 3 тестового задания.

## 1. Применённые инструменты и промпты

**Инструменты:** ChatGPT / Claude (генерация кода, проектирование, отладка), Cursor
(автодополнение и рефакторинг), встроенный AI-ассистент IDE. Ниже — конкретные промпты и их
назначение.

| Назначение | Промпт |
| ---------- | ------ |
| Проектирование | «Спроектируй REST API для приложения „Погода с настроением“: эндпоинты, модель данных, ML-подсистема. Стек — FastAPI + React + SQLite». Результат лёг в основу `docs/design.md`. |
| Генерация кода | «Напиши FastAPI-эндпоинт текущей погоды через Open-Meteo с кэшем в SQLite (TTL 10 минут) и детерминированным mock-fallback». Результат — `weather_service.py`. |

## 2. Анализ эффективности

### Где AI ускорил разработку

- **Каркас и boilerplate.** Скелет FastAPI (роуты, Pydantic-схемы, конфигурация) и React-компоненты
  сгенерированы за минуты, что освободило время на содержательную часть — ML и UX.
- **Отладка.** Диагностика `DetachedInstanceError` и формата parquet заняла один запрос вместо
  получаса чтения документации.
- **Проектирование.** Черновик структуры API и модели данных дал готовую основу для `design.md`.

### Где AI ошибся или требовал серьёзной корректировки

- **Стратегия категоризации.** Первоначальное предложение — категоризировать весь датасет мемов
  чисто по эмбеддингам (zero-shot). После проверки на реальных данных выяснилось, что набор мемов
  общий, погодных — меньшинство, и результат шумный (например, «солнцезащитные очки» тянуло в
  «жару», «ветеринар» — в «ветер»). Обнаружил ручной выгрузкой выборки по категориям. Исправил:
  seed строится детерминированным keyword-отбором со списком исключений, а эмбеддинги применяются
  для открытых текстов — авто-категоризации пользовательских мемов.
- **Сгенерированный код падал в рантайме.** Дважды: `column.field("bytes")` не работает для
  `ChunkedArray` (нужен `.flatten()`), и первая версия пайплайна не была идемпотентной — массовый
  `query.delete()` не запускал ORM-cascade и при повторном запуске возникал `IntegrityError`.
  Оба случая нашёл smoke-тестом и прогоном на реальных данных.
- **Версии и совместимость.** AI-предложение тянуть `sentence-transformers` (torch) было избыточным
  для задачи; после уточнения выбрана лёгкая ONNX-альтернатива `fastembed`.

### Где я сознательно отказался от предложения AI

- **Классификатор «погода → категория» (RandomForest).** Отказался: категория и так детерминирована
  по WMO-коду и порогам температуры/ветра, ML здесь был бы «ML ради ML». Перенёс ML-бюджет туда,
  где он даёт реальную ценность — рекомендатель и семантическое тегирование.
- **Тяжёлые эмбеддинги через torch.** Отказался ради простоты развёртывания на Linux/Windows без
  многогигабайтной зависимости.

## 3. Выводы и рекомендации

1. **AI кратно ускоряет boilerplate и отладку**, но его ответы нужно верифицировать на реальных
   данных. Два сгенерированных фрагмента падали в рантайме, и оба нашлись только прогоном.
2. **Границы применимости ML определяет человек.** AI охотно предлагает «ML для всего», но честное
   инженерное решение — детерминированная логика там, где она достаточна, и ML там, где он учится
   (оценки пользователей, открытые тексты).
3. **Конкретные промпты с контекстом** (стек, ограничения, ожидаемый формат) дают заметно более
   качественные черновики, чем общие запросы.

**Советы коллегам, начинающим использовать AI:**

- Генерируйте черновики, но всегда прогоняйте код (smoke-тест, тесты) — AI-код без проверки опасен.
- Проверяйте предложения на реальных данных, а не «на глаз».
- Фиксируйте, где вы отклонили ответ AI и почему — это дисциплинирует и помогает учиться.
